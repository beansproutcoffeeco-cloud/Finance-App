# 17hats: Projects & Client Portal

Research date: 2026-07-07. Method note: 17hats' own domains (help.17hats.com, 17hats.com, blog.17hats.com, 17hats.releasenotes.io) were not directly fetchable from this environment (proxy policy denial), so this document is synthesized from extensive web-search extraction of those pages plus third-party reviews. All source URLs are listed in §9. Items marked **[uncertain]** could not be fully verified.

---

## 1. Summary

- The **Project** is 17hats' central organizing object — explicitly described in their docs as "a manila file folder with the person's name on it." Every email, document (quote/contract/invoice/questionnaire), uploaded file, note, to-do, event, phone log, and time log hangs off a Project.
- A Project belongs to exactly **one primary Contact**, but a Contact can have **many Projects** (e.g., a returning photography client gets one project per session/year). Additional people are attached as **Related Contacts** (can be CC'd on emails and added as contract co-signers).
- Projects are **internal-only**; clients never see the Project page. Clients interact through **document links** and the **Client Portal** — a per-contact (not per-project) secure page where they can accept quotes, sign contracts, pay invoices, complete questionnaires, view event details, and edit their own contact info.
- 17hats has **no true "project stages" field**. Progression is modeled by three overlapping mechanisms: **Lifecycles** (legacy visual stage indicator with triggers), **Project Tags** (free-form labels used for assignment, categorization, and filtering), and **Pipelines** (2024+ feature: tag-driven kanban-ish phase boards, up to 5 phases each).
- Task management is deliberately lightweight: flat **To-Dos** (manual or generated by **Workflow** templates composed of To-Do / Action / Pause steps). No subtasks, no dependencies, no kanban/Gantt, no per-task assignee field (assignment is faked with tags/calendars).
- Client Portal auth is **link-based with optional password (PIN)** — no client accounts, no magic-link expiry noted, plus a "Universal Client Portal Link" login page for password-protected portals. Branding = logo + cover image + welcome message + custom subdomain.
- Portal is read/complete-only: clients **cannot upload files, message, or see tasks/progress** — the most-cited weakness in reviews, along with a dated UI.
- Everything above is directly buildable: the data model inferred in §6 (Contact ⟶ Projects ⟶ polymorphic attachments + ContactPortalSetting) matches 17hats' own template tokens (e.g., `[% project.client.portal_url %]`, `[% project.client.contact_portal_setting.pin %]`).

## 2. Project model

### 2.1 Concept & positioning

- 17hats defines a Project as the "central location for all information about the service you are providing to your lead or client." Docs repeatedly use the manila-folder metaphor.
- **Contacts vs Projects**: A Contact is a person/company record classified into one of four **contact types** — `Lead`, `Client`, `Cold Prospect`, `Other`. A Project is the container for work done for that contact. Without a project there is "nowhere to organize your contact's information or documents" — i.e., most operational objects *require* a project, not just a contact.
- **Project creation paths**:
  - Automatically when a **Lead Capture Form (LCF)** is submitted (contact created as type Lead + a new Project started, with optional auto-applied contact/project tags, auto-response email, and auto-triggered Workflow).
  - Automatically via **Online Scheduling** bookings (booking creates/attaches to a project; the auto-created invoice lands in the project).
  - Manually from a contact record ("+ new project").
- The **Project page is internal-only**. Client-visible surfaces are per-document share/view links and the Client Portal.

### 2.2 What a Project holds (Project page layout)

Top of page:
- **Project Details** block: by default shows **Project Title, Primary Email, Project Date, Phone Number, Contact Type, and assigned Calendar**; more fields appear as they're filled. Date/time/location of the project shown at top for quick reference and auto-added to the Calendar. Edited via pencil icon next to project name or Edit > Edit Project.
- **Custom Project Fields**: user-defined fields (created in Account Settings > Custom Fields, each with a chosen format/type). They appear in the Project Details section once populated, and are usable as **tokens** in emails/contracts and mappable from Lead Capture Forms and Questionnaires. (Custom *Contact* Fields exist in parallel on the contact record.)
- **Client Portal bar** under the contact's name (expand to configure that contact's portal — see §5).
- **Related Contacts** section.
- **Important Documents** section: all created/sent/completed **Quotes, Contracts, Invoices, Questionnaires** for this project, with a **"Create New"** button to spawn a new document in-context. Only 17hats-native documents appear here (not uploaded files).
- **Workflows** applied to the project (each applied workflow is a *copy* of the template — see §3).

Bottom of page — **activity tabs** (each tab has a `+` button to add an entry):
1. **Notes** — free-text project notes; 17hats auto-timestamps each entry (time + date). Answers from LCFs, Questionnaires, and Online Scheduling questions can be **mapped directly into Project Notes**.
2. **Emails** — synced correspondence (see §2.5).
3. **Files** — uploads of outside documents (PDF, JPEG, etc.). Files here are **not** shown in the Client Portal. (No storage limit documented in accessible sources — **[uncertain]**.)
4. **To-Do's** — project task list (see §3).
5. **Events** — calendar events attached to the project (an event can be designated as *the* Project Date, or just live in the Events tab). Google Calendar events can also be attached to a project.
6. **Phone Log** — manual log of calls. (Feature confirmed as a tab; details sparse in accessible sources.)
7. **Time Log** — time-tracking entries (see §2.6).
8. **Activity Log** — audit trail of what happened on the project. (Contents not fully documented in accessible sources — **[uncertain]** exactly which events it records.)

### 2.3 Stages, statuses, lifecycles, pipelines

17hats has *three* generations of "where is this project in my process" tooling, all still coexisting:

**(a) Project status (system-level):** effectively `Active` / `Archived` / `Deleted` (+ implicit "Completed" via a marker):
- **Archive**: Edit > Archive Project. Archiving hides all related To-Dos and events from the calendar, suppresses all notifications (incl. workflow notifications), stops ALL email reminders, and **cancels all active recurring invoices** in the project. Projects list can be filtered Active vs Archived. Unarchive via Edit > Unarchive.
- **"Mark complete"**: there is a help article "How do I mark a project as complete?" — completion is closely tied to archiving and (in Pipelines) hitting a success marker; 17hats does not appear to have a distinct first-class "completed" status separate from archive **[uncertain]**.
- **Delete**: permanent removal of the project, its documents, and its bookkeeping records — but a **Restore** area (Account Settings > Restore) lets you recover Contacts and Projects deleted within the **last 30 days**; restoring a project restores its contact (and a contact deleted within 10 minutes of its project restores both together).

**(b) Lifecycles (legacy visual stage bar):** one Lifecycle per project (many Workflows allowed). A lifecycle is a named sequence of stages (e.g., New Lead → Meeting → Booking) that "displays what has already occurred" — a visual aid, not an automation engine. Each stage:
- has a custom **name**;
- starts on a **trigger** (e.g., contract sent, invoice paid);
- can **swap the project's assigned calendar** (e.g., move from "Lead Calendar" to "Booked Calendar") and change the project date's calendar color-coding.
A default starter lifecycle ships with the account; stages can be added/deleted/renamed. Lifecycles and Workflows are independent — you can use either or both.

**(c) Pipelines (modern, 2024+):** visual boards showing where leads/clients are in the journey.
- Limits: up to **7 active Lead Pipelines** and **5 active Client Pipelines**; each pipeline has up to **5 Phases**.
- **Project Tags move projects into, through, and out of pipelines** — a phase is bound to a tag ("By Tag" phase type: add the tag → project appears in that phase) or advances automatically "By Days in Prior Phase" (time-based).
- Pipeline-level project states: **Active** (in a phase), **Completed** (hit the pipeline's **success marker** and exited), **Removed** (archived, deleted, or tags removed).
- Tags (and thus phase transitions) can be added/removed automatically by Workflow action steps (Send Questionnaire/Quote/Contract/Invoice/Email, Archive Project, Confirm Booking).
- Reviewers still note 17hats has **no true kanban board, Gantt chart, timeline, task dependencies, or subtasks** — Pipelines are a high-level funnel view, not task management.

**(d) Lead→Client conversion:** contact type changes from Lead to Client automatically when a **quote is accepted** (and its attached invoice becomes available) and/or contract signed; can also be changed manually. "Confirm Booking" exists as a workflow action step.

### 2.4 Tags

- Two tag families: **Contact Tags** and **Project Tags** (separate lists, both plain strings).
- Applied by editing the project (Edit > Edit Project > Tag field; type-ahead against existing tags; Enter creates a new one; shows as a blue chip).
- Uses: categorize project types (e.g., Newborn / Corporate Headshot), **assign projects to team members** (tag = person's name — this is 17hats' official answer to "assignment"), mark years/locations/sources, and **drive Pipelines**.
- **Filtering/search**: Projects page search bar filters by tag; tags also filter Contacts, Leads, and Recent Client Activity pages. Filtered sets enable **bulk actions**.
- **Automation**: LCFs auto-apply tags on submission; **Advanced Workflows** (Premier plan) have an Add/Remove Tags step for contacts and/or projects (e.g., remove `Lead`, add `Booked` on booking).
- **Tag Management** (Account Settings): rename, **merge**, and delete tags globally.

### 2.5 How emails, documents, invoices attach to projects

- **Documents (Quotes, Contracts, Invoices, Questionnaires)** are created *from within* a project ("Create New" in Important Documents) and are inherently project-scoped; sending happens right after creation via an email prompt. Invoices created by Online Scheduling are auto-filed into the contact's project and surfaced in the Client Portal, the Documents tab, and Recent Client Activity.
- **Emails**: 17hats syncs connected inboxes roughly **every 30 minutes** (up to ~65 min lag) and files an incoming message into a project only if (1) the sending address is connected in Email Settings' Incoming Email, (2) the From address matches a **contact record**, and (3) that contact has an **active project**. Non-matching mail stays out/un-assigned. All contact emails are "filtered into 17hats and stored directly in their Project." Outbound templated email supports **tokens** (see §6.4). Email correspondence lives **only** on the project page — clients don't see it in the portal.
- **Files**: manual uploads on the Files tab; excluded from Important Documents and from the Client Portal.
- **Related Contacts** can be added to any email To/CC via a Contacts dropdown and added as extra **signees** on contracts (primary signs first, then secondary). The **primary contact receives all confirmation emails** for anything a related contact signs/pays/completes.
- **Move Projects between Contact Records** is supported (help article exists) — reparenting a project to a different contact.
- **Bulk actions** on Projects list (list view, checkbox select): add/remove tags, archive, delete, apply workflows in bulk. Same bulk pattern exists for documents.

### 2.6 Time tracking & invoicing from a project

- Global **Timer** button (any page) → pick project → select or create a **rate** ("task" dropdown); manual time entry with date also supported.
- Only **one running timer per account** (even with multiple users) — a notable limitation.
- Entries appear on the project's Time Log tab; a green **Invoice** button converts logged time into an invoice (option to include non-billable time and to show tracked dates).
- Time tracking is a paid add-on / higher-tier feature per reviews **[uncertain on current packaging]**.

### 2.7 Projects list page

- Toggle between **tile view and list view** (two icons at top).
- Search bar doubles as tag filter; Active/Archived filter from the project menu.
- List view checkboxes → **Bulk Actions** dropdown (tags, archive, delete, apply workflow).

## 3. Tasks & to-dos

### 3.1 To-Do basics

- To-Dos are flat checklist items with a **due date**, attached to a project (or standalone) and assigned to a **calendar** (17hats' recommended convention: create dedicated calendars for "Leads," "Booked/Paid Clients," and "To-Do & Workflow Items" so tasks don't clutter booking calendars).
- Where they surface: Dashboard "Let's Take Care of Business" section (**only due or past-due** items), the **To-Do page** (all tasks incl. completed), the **Calendar**, the **Quick Look sidebar** (right-edge slide-out with schedule + due/upcoming to-dos + quick-add), and the project's To-Do tab.
- **Auto-purge**: to-dos past due **2+ months are automatically removed** — an unusual, opinionated behavior.
- To-Do items sync state with Google Calendar per a dedicated FAQ (whether they appear on synced Google calendars) **[uncertain: exact sync behavior]**.
- **No per-task assignee field** — assignment is emulated with project tags or separate calendars. No subtasks, dependencies, priorities, or kanban (confirmed by competitor teardown and reviews).

### 3.2 Workflows = task/automation templates (17hats' "project templates")

17hats has **no "project template"** object (no duplicate/copy-project function found). The reusable-process primitive is the **Workflow Template**:

- A Workflow Template is an ordered list of steps of three types:
  1. **To-Do items** — appear on your calendar/task list; can be set to fire something automatically upon check-off (e.g., check off "review lead" → follow-up email sends). Can be completed "automatically or upon your review."
  2. **Action items** — 17hats does the thing: **send Email / Quote / Contract / Invoice / Questionnaire (from templates), start another Workflow, archive the project, change the project's calendar, add/remove tags (Advanced), confirm booking**.
  3. **Pause items** — a break that holds the sequence until a date or until manually resumed; commonly anchored to the session/project date. Unlimited pauses allowed; they don't appear on the calendar.
- **Scheduling is relative to a Base Date**: each step is offset (e.g., "2 days after base date"). The Base Date typically = **Project Date** but can be set independently — reviewers call the base-date-vs-project-date distinction "so CONFUSING."
- **Activation**: applying a workflow to a project **copies** the template's steps into the project. Triggers: automatically from a Lead Capture Form (including branch-by-answer: a "Choose from a List" question can trigger a different workflow per answer choice), from another workflow (chaining), from Online Scheduling bookings, applied **in bulk** from the Projects page, or manually.
- **Template edits don't propagate** to already-applied copies — you must edit the in-project workflow or re-apply. (Real UX pain point.)
- **Advanced vs Basic Workflows**: higher plan tiers unlock advanced steps (auto tag add/remove, richer automation); Basic plans get simpler sequences. Template **Sharing/Marketplace**: email/document/LCF/scheduling/workflow templates can be shared between accounts via access codes (Premier tier) — a template ecosystem exists.
- Multiple workflows can run on one project simultaneously.

## 4. Project lifecycle & UX flows

### 4.1 Canonical happy path (as 17hats documents it)

1. **Lead captured** — LCF submission auto-creates Contact (type Lead) + Project, applies tags, sends auto-response, triggers Workflow. Dashboard notification appears; lead also listed on the Leads page.
2. **Respond/quote** — workflow action sends Quote (optionally a **Combined Document**: quote + contract + invoice chained). Client acts via link or portal.
3. **Booking** — quote accepted → attached invoice becomes payable → contact **auto-converts Lead → Client**; contract signed; "Confirm Booking" step; lifecycle stage trigger can flip the project onto the "Booked" calendar; workflow tag changes move the project along a Pipeline.
4. **Fulfillment** — to-dos fire relative to project date; questionnaires gather info (answers can map into project notes/custom fields); events tracked; time logged; portal keeps client self-served.
5. **Completion** — final invoice paid; workflow can **auto-archive the project**; pipeline success marker records completion; project archived (notifications/reminders/recurrences stop).

### 4.2 Notifications & activity surfaces

- Owner email alerts on client actions (e.g., "A quote has been accepted"); automatic **confirmation emails to clients** when they complete a quote/contract/invoice/questionnaire (customizable under Account Templates; can be disabled under Email Settings > Confirmations).
- **Document email reminders**: automated nag emails for unactioned documents (per Email Settings).
- **Recent Client Activity** page: last-5-documents feed on dashboard + full page filterable by Client, Project, Activity type, Tags, with a **Snapshot** counter (questionnaires completed / quotes accepted / contracts signed / invoices paid).
- Mobile apps (iOS/Android) exist with access to core objects **[uncertain: exact project-page parity]**.

### 4.3 Multi-user

- Users can be granted permissions per feature area; a permission toggle controls whether a team member can use **Time Tracking** (start timer on a project, choose a rate). Project "assignment" to users = tags (§2.4). Per-project access control does not appear to exist **[uncertain]**.

## 5. Client Portal

### 5.1 Model & provisioning

- A portal is **automatically created for every Contact** (portal is per-contact, aggregating all their active projects — not per-project).
- By default it displays **all sent documents from all active projects** for that contact; archived projects drop out; per-project filtering can hide chosen projects.
- A **universal on/off switch** can enable/disable Client Portal for ALL contacts at once (release-note feature), plus per-contact enable/disable.

### 5.2 Auth / access (no client accounts)

- Access is via a **unique portal URL per contact** — no username/password account creation for clients.
- URL lives on the business's **custom subdomain**: `{subdomain}.17hats.com/...` (subdomain set in Brand Preferences; also rebrands quote/contract/form share links). Exact path shape undocumented publicly **[uncertain]**.
- Optional **password protection (PIN)** per contact: toggling on generates a random string, editable to something memorable.
- Delivery: an **"E-mail Link" button** on the Client Portal bar opens a pre-built, editable email template containing the portal URL and (conditionally, via an `[IF] Password Protected` block) the PIN. Tokens: `[% project.client.portal_url %]`, `[% project.client.contact_portal_setting.pin %]`. Can also be sent automatically by a workflow email step.
- **Universal Client Portal Link**: a single account-level login page URL where password-protected clients can sign in (useful for a "Client Login" button on the business website).
- No documented link expiry, 2FA, or magic-link re-issuance flow — it's effectively a capability URL + optional static PIN. **[uncertain: session/expiry mechanics]**

### 5.3 What clients can see & do

Can:
- **View + complete documents**: accept **Quotes**, sign **Contracts**, pay **Invoices**, fill **Questionnaires** — same actions as the direct document links, gathered in one place.
- **View event details**: date, time, location for all project events.
- **View/edit their own contact information** (self-service data hygiene).
- Read the **Welcome Message** (rich text/links/images).
- Via Online Scheduling (separate booking pages, linked/embedded rather than a portal tab **[uncertain: whether booking is surfaced inside portal UI]**): book, **reschedule, cancel** appointments; auto-created invoices then show in the portal.

Cannot:
- **Upload files** (explicitly documented).
- See **emails/correspondence**, internal **Files**, **Notes**, **To-Dos/tasks**, project progress, deliverable status, or timelines (no PM data exists to show; confirmed by user Q&A and competitor teardowns).
- Message the business (no portal chat/comments).

### 5.4 Business-side customization

Global (Account Settings > Client Portal), with **live preview**:
- **Cover Image** (recommended 1140×220px) at top of portal.
- **Logo** toggle (pulled from Brand Preferences).
- **Default Welcome Message** (text, links, images) for all portals.
- Global document-type toggles: show/hide **Quotes, Contracts, Invoices, Questionnaires** portal-wide.

Per contact (Client Portal bar on the project page):
- Enable/disable portal; set/change **password**; override **welcome message** per contact **[uncertain — custom welcome messages confirmed, per-contact override strongly implied by "Customizing per Contact" docs]**.
- **Per-document-type toggles** overriding global (e.g., invoices only). Caveat from docs: changing one toggle overrides the previously viewable set (fiddly behavior).
- **Project Filtering**: per-project show/hide toggle; hiding removes that project's events, details, and documents from the portal (added as "Client Portal Filtering" feature release).

Branding beyond the portal: custom subdomain, brand colors/fonts on documents, logo on emails/docs — the portal inherits the same brand kit.

### 5.5 Reviewer sentiment on the portal

- "A little clunky looking to clients," "not as beautiful as others," "wish it were more than just a viewing area."
- Competitors (HoneyBook, Dubsado, Plutio, ManyRequests) position richer portals (messaging, file sharing, progress) against it.

## 6. Inferred data model

Reconstructed from documented behavior + 17hats' own token grammar (`project.client.portal_url`, `project.client.contact_portal_setting.pin` reveal real association names). Not an official schema.

### 6.1 Core entities

```
Account (business)
├─ User (team member; per-feature permissions incl. time-tracking flag)
├─ BrandPreference (logo, colors, fonts, custom_subdomain)
├─ ClientPortalGlobalSetting (cover_image, show_logo, default_welcome_message,
│    show_quotes, show_contracts, show_invoices, show_questionnaires, portal_enabled_all)
├─ Calendar (many; projects/events/to-dos assigned to one)
├─ Tag (name, kind: contact|project)  — global list; rename/merge/delete
├─ CustomFieldDefinition (name, format/type, scope: contact|project)
├─ Template (kind: email|quote|contract|invoice|questionnaire|lcf|scheduling_service|workflow)
├─ Lifecycle (stages[]: name, trigger_event, target_calendar_id)
└─ Pipeline (kind: lead|client, max 5 phases)
     └─ Phase (type: by_tag(tag_id) | by_days_in_prior_phase(n), success_marker?)

Contact
├─ type: lead | client | cold_prospect | other
├─ core fields: first/last/company/email/phone/address...
├─ custom_field_values (per CustomFieldDefinition)
├─ tags (contact tags, M:N)
├─ ContactPortalSetting (1:1)  ← token: contact_portal_setting
│    ├─ enabled, portal_url (unique capability URL), pin (nullable password),
│    ├─ welcome_message_override?, show_quotes/contracts/invoices/questionnaires overrides
│    └─ hidden_project_ids[] (project filtering)
└─ projects (1:N)

Project
├─ contact_id (primary contact, 1) — re-parentable ("move between contact records")
├─ title, project_date (nullable), start/end time, location
├─ calendar_id (assigned calendar; lifecycle triggers can change it)
├─ status: active | archived (+ soft-delete with 30-day restore window)
├─ tags (project tags, M:N)  → drive pipeline phase membership
├─ custom_field_values
├─ related_contacts (M:N Contact, role: cc/signee)
├─ lifecycle_instance (0..1; current_stage)
├─ pipeline_membership (derived from tags; state: active|completed|removed)
└─ children (all 1:N):
     Documents (Quote|Contract|Invoice|Questionnaire; status: draft/sent/viewed/
                accepted|signed|paid|completed; share_url)
     EmailMessages (synced in ~30-min polls; matched by contact email + active project)
     FileUploads (internal only)
     Notes (body, auto timestamp; can be auto-filled from form answers)
     ToDos (title, due_date, calendar_id, completed_at, source: manual|workflow,
            auto_send_on_complete?; auto-purged 2 months past due)
     Events (title, date/time, location, calendar_id, is_project_date flag,
             external google_event_id?)
     PhoneLogEntries
     TimeLogEntries (rate/task, duration or start/stop, billable flag, date,
                     invoiced_invoice_id?)  — 1 running timer per account
     ActivityLogEntries (audit)
     WorkflowInstances (copied steps from WorkflowTemplate)
```

### 6.2 Workflow engine sketch

```
WorkflowTemplate { name, steps[] (ordered) }
Step {
  type: todo | action | pause
  offset: {n, unit, direction} relative to base_date | prior step | pause-until
  todo: { title, calendar_id, auto_send_template_id?, requires_approval }
  action: { verb: send_email|send_quote|send_contract|send_invoice|send_questionnaire|
                  start_workflow|archive_project|change_calendar|add_remove_tags|confirm_booking,
            template_id?, tags_add[], tags_remove[] }
  pause: { until: date|manual }
}
WorkflowInstance { project_id, template_id, base_date, steps[] (materialized copy),
                   state per step }   // template edits do NOT propagate
Triggers: lcf_submission (incl. per-answer branching), scheduling_booking,
          parent_workflow_step, bulk_apply, manual
```

### 6.3 Portal rendering rule (effective visibility)

```
visible_docs(contact) =
  for project in contact.projects where project.status == active
                                   and project.id not in hidden_project_ids:
      docs of enabled types (per-contact overrides ?? global toggles)
+ events of those projects (date/time/location only)
+ contact self-profile (editable)
+ welcome message (contact override ?? global)
Auth: GET portal_url [ + PIN check if set ]; account-level universal login page for PIN'd portals.
```

### 6.4 Token grammar (template merge fields)

- Contact: first/last/full name, company, address, email, phone.
- Project: name, location, date, start time, end time (+ integration tokens like ShootProof gallery).
- Account/user: first/last/full name, company.
- Scheduling service: service name, location name/address, booking date/start/end, duration.
- Portal: `[% project.client.portal_url %]`, `[% project.client.contact_portal_setting.pin %]`; conditional blocks like `[IF]: Password Protected`.
- Custom fields usable as tokens in emails/contracts, and populated from LCFs/questionnaires.

## 7. Strengths / weaknesses

### Strengths (to emulate)

1. **Single-folder mental model** — one project page with every artifact (docs, mail, money, tasks, time, events, notes) is the product's core loved feature; reviewers consistently praise the centralization.
2. **Auto-filing of email** into the right project by contact-match is high-value glue no lightweight competitor does well.
3. **Multiple projects per contact + per-contact portal** cleanly handles repeat business; related contacts solve the two-signers/spouse/planner case.
4. **Tags as a universal, automatable primitive** (filtering, team assignment, pipeline movement, bulk ops, workflow-driven add/remove) — cheap to build, very leveraged.
5. **Workflow steps that mix human to-dos with system actions + pauses** anchored to a base date — genuinely automates the solopreneur client lifecycle.
6. **Portal simplicity**: no client account creation friction; one link (optionally PIN'd) to everything they must sign/pay/answer; live-preview branding.
7. Safety rails: 30-day restore of deleted contacts/projects, archive semantics that silence reminders/recurrences, bulk actions.

### Weaknesses / user complaints (opportunities)

1. **Dated, clunky UI**; portal "not beautiful," dashboard overwhelming; steep learning curve (consensus complaint; 7-day trial too short to learn it).
2. **Portal is read/complete-only**: no client uploads, no messaging, no task/progress visibility — top requested gap.
3. **Fragmented stage tooling**: Lifecycles vs Tags vs Pipelines is three overlapping systems; pipelines capped (7/5 pipelines, 5 phases) and tag-driven only.
4. **Task management too thin**: no assignees, subtasks, dependencies, kanban/Gantt; to-dos silently auto-delete 2 months past due; single account-wide timer.
5. **Workflow template edits don't propagate** to applied copies; base date vs project date confuses users.
6. Email sync latency (30–65 min) and only-if-active-project matching drops mail.
7. Per-contact portal toggle quirk (one change overrides prior toggle set) — fiddly settings UX.
8. **Data hostage on cancellation** (records inaccessible immediately unless pre-exported); add-on pricing (bank connect, time tracking, recurring billing) contradicts "all-in-one" positioning.
9. Auth is a static capability URL + optional static PIN — weak by modern standards (no expiring magic links, no 2FA).

## 8. Build recommendations

**Copy (proven, cheap, loved):**
- Project = folder-per-engagement under a Contact; N projects per contact; polymorphic attachment tabs (notes/emails/files/tasks/events/time/activity) + a pinned "Important Documents" rail with in-context "Create New."
- Per-contact portal aggregating active projects, with per-project hide, per-doc-type toggles, welcome message, logo/cover branding, custom subdomain, and one-click "email portal link" template with tokens.
- Tags with type-ahead, merge/rename admin, bulk actions, and automation hooks; auto-tag from intake forms.
- Workflow templates (todo/action/pause, offsets from base date, LCF/booking triggers, branching by form answer); owner + client confirmation emails; Recent Client Activity feed with snapshot counters.
- Archive semantics (silence everything, cancel recurrences) + 30-day trash/restore.

**Improve (differentiators):**
- **One stage system, not three**: first-class customizable project stages rendered as a real kanban, with tag- and event-based automations — replaces Lifecycles+Pipelines.
- **Two-way portal**: client file uploads, threaded comments/messages per project, and optional visibility of selected tasks/milestones ("what we need from you" checklist) — directly answers the top complaints.
- **Modern auth**: expiring magic links with re-request, optional passwordless email OTP; keep the zero-account friction.
- **Real task fields**: assignee, reminders, recurrence; propagate-template-updates option (or versioned workflows); multiple concurrent timers per user.
- Instant email ingestion (webhook/IMAP IDLE) with an "unassigned inbox" triage view instead of silently dropping non-matching mail.
- Live portal settings preview (copy) but with additive toggles (fix the override quirk).
- Full data export at any time + read-only grace period after cancellation (trust wedge vs 17hats).

**Skip (low value / dead weight):**
- Lifecycles as a separate visual-only object; per-account single timer; tag-as-assignment hack (build real assignment); to-do auto-deletion; separate tile/list project views (one good table with saved filters suffices); marketplace/template-sharing until there's a user base.
